# WP12 — PHP 8.5 toolchain and static compatibility scans (parts 1 and 2, review fixes)

Scope (DESIGN.md §13.2 WP12, §11.8, §12.6): the Option A PHP 8.5 toolchain in the scratchpad with checksum
verification, `bin/php85-scan.sh` in lint with the `--min=8.1` floor rules, `bin/compat-api.php` for the WordPress 6.5
/ WooCommerce 8.0 API floors, seeded-violation fixtures proving each scan detects, the optional `compat-min` site on
port 8797, a first lint, unit and integration run on PHP 8.5, fixes for what those runs found, and the same three runs
on PHP 8.3 again.

Part 1 (tooling, in the scratchpad only) built the toolchain, the two scans with their fixtures and the compat-min
site. Part 2 (this package's repository work) moved the scans into `bin/`, wired them into lint, added the unit
tests, ran everything on both PHP versions, fixed what was found, and ran compat-min. A review of part 2 then
reported five gaps in the scans; all five were reproduced and fixed with regression checks, and lint, unit,
integration and the build were run again on both PHP versions (§8, results in §3).

`S` is the session scratchpad of DESIGN.md §12.1. Paths are relative to this folder unless they start with `S/`. All
commands ran from this folder with `nice -n 10`; every PHPUnit and integration run was wrapped in
`flock S/lga-suite.lock`, one at a time; servers only on 8793, 8794 and 8797, all stopped afterwards. No `wp-api` tool
was used, nothing outside this folder and the scratchpad was changed, and no commit was made.

## 2. The scans

| File | What it is |
|---|---|
| `bin/php85-scan.sh` | Entry point (`bash bin/php85-scan.sh [--min=8.1] [--root=DIR] [--no-lint] [PATH …]`): runs the rules, then `php -l` with the oldest PHP it finds (`php`, `php8.1`…`php8.5`, `/usr/bin/php8.*`, `LGA_PHP_LINT`), always with `-n`. Exit 0 clean, 1 findings, 2 usage error. The rules run on `$PHP` (default `php`). |
| `bin/php85-scan.php` | Rule engine: the §11.8 deprecation list, the deprecations PHP 8.5.13 really raises beyond it (`$http_response_header`, driver-specific PDO constants and methods, one-argument `new ReflectionMethod`, `E_USER_ERROR`, `"${}"`, functions and constants deprecated in 8.1-8.4), and with `--min=8.1` the 8.2, 8.3, 8.4 and 8.5 syntax, functions, classes and methods of §11.8 on the shipped files. Accepts `function_exists`/`class_exists`/`method_exists` and `PHP_VERSION_ID`/`version_compare` guards (if/elseif/else, early returns, `&&`, `\|\|`, `?:`); a runtime deprecation inside a `PHP_VERSION_ID < X` branch is not reported, a compile-time one always is. A polyfill counts only when a floor file declares the function under the name the call resolves to (§8). Constants are matched in both forms, `NAME` and `\NAME`; null offsets as `[null]`/`[\null]`, `array_key_exists(null, …)` and null keys of array literals. |
| `bin/compat-api.php` | WordPress / WooCommerce API floors: tokenizes the main file, `uninstall.php` and `includes/`, collects called functions, classes (`new`, `::`, `extends`, `implements`), static methods and hook names, and looks each up in the WordPress and WooCommerce source of `LGA_WP_PATH` (or `--wp=`): lowest `@since` of the declaration (for a hook, of the doc comment of the `do_action`/`apply_filters` call). Floors from the plugin header (6.5.0 / 8.0.0); Action Scheduler symbols against 3.6.1, the release bundled with WooCommerce 8.0. Guards: `function_exists`/`class_exists`/`method_exists`, `version_compare( get_bloginfo( 'version' ) \| $wp_version \| WC_VERSION … )`, `is_wp_version_compatible()`. Symbols without `@since` are "unknown", not failures. Exit 0, 1 failures, 2 usage, 3 not run (no WordPress or WooCommerce source). Not checked: instance methods and constants. |
| `bin/scan-lib.php` | Shared token view (`Source`), guard tracker (`Guards`), version helpers and the file collector (`Files`). A guard branch without an `else` guards the code after it when its first statement leaves (return, throw, exit, continue, break, `wp_die()`) or requires/includes a file, or for exactly the functions and classes it declares itself (§8, finding 3). |

**Lint wiring** (`bin/lint.sh:30-44`): after the neutrality scan, `bash bin/php85-scan.sh --min=8.1`, then
`php bin/compat-api.php`; exit 3 prints `compat-api: not run (set LGA_WP_PATH …)` and does not fail lint, any other
non-zero exit fails it. Both scans need only the `php` on PATH: with PHP 8.3 alone (no PHP 8.5 toolchain on PATH)
lint runs both scans, and the `php -l` step picks the oldest PHP (8.3.6) whichever PHP runs lint.

**Default targets and the fixtures.** The seeded violations live in `tests/fixtures/compat-scan/`. Both scans leave
out exactly that folder (`Files::FIXTURES`, compared by equal relative path in `Files::collect()`'s new `$skipPaths`,
`bin/scan-lib.php:896-951`): `tests/fixtures/compat-scan-extra/`, `tests/fixtures/other/compat-scan/` and
`tests/Unit/compat-scan/` are still scanned (unit test below). php85-scan's default target is the main file,
`uninstall.php`, `includes/`, `tests/` and `bin/` (floor: the first three); compat-api's is the main file,
`uninstall.php` and `includes/`. The PHP 8.4/8.5 syntax fixtures use the `.php.fixture` extension, so lint's own
`php -l` loop on PHP 8.3 never reads them; the `.php` fixtures are valid PHP 8.3. The fixtures pass the neutrality
scan (lint: "Neutrality OK (repo)", the source ZIP: "Neutrality OK (source)").

## 4. Fixes (each with what found it and the evidence before and after)

1. **`tests/Support/FakeWpdb.php:22-44`** (test helper). `PDO::sqliteCreateFunction()` is deprecated in PHP 8.5.
   Found by php85-scan (part 1: 3 findings at lines 25-27, `pdo-driver-method`) and by the unit suite on PHP 8.5
   (part 1: `OK, but there were issues! … Deprecations: 3`). Now `Pdo\Sqlite` with `createFunction()` on PHP 8.4+
   (`PHP_VERSION_ID >= 80400`) and the old call below 8.4. After: php85-scan 0 findings, unit on 8.5 0 deprecations.
2. **`includes/Repositories/Backlinks.php:129-140`** (shipped code). `weeklyTrend()` used the row's week (`wk`) as an
   array key; for a row whose week cannot be computed it is NULL, and PHP 8.5 deprecates a null offset. Found by
   the first integration run on PHP 8.5: 12 lines "Using null as an array offset is deprecated" from
   `Backlinks.php:130` and `:135` in the site's debug.log (on the LGA site the SQLite translation returns NULL for
   `DATE_FORMAT(…, '%x-%v')`). php85-scan cannot see it (the key is a runtime value). Fix: `(string) ( $r['wk'] ?? '' )`
   as the key, same result (the `''` key never exists). Regression test `tests/Unit/Repositories/BacklinksTrendTest.php`:
   before the fix it fails on PHP 8.5 (exit 1, deprecations at Backlinks.php:130 and :135, through
   `failOnDeprecation`) and passes on 8.3; after the fix it passes on both.
3. **`includes/Admin/Assets.php:34, 50-64`** (shipped code, WordPress 6.5 floor). On WordPress 6.5 the plugin's
   dashboard got no script at all: `wp_enqueue_script_module()` exists since 6.5, but 6.5 prints script modules
   only in `wp_head`/`wp_footer`; the `admin_print_footer_scripts` printers arrived in 6.6.0 (checked against
   `class-wp-script-modules.php` of WordPress 6.5.15 on the compat-min site, 7.1.4 on the LGA site, and the
   wordpress-develop tags 6.6.0 and 6.7.0 fetched read-only into the scratchpad and deleted afterwards). compat-api
   cannot see it (every function exists in 6.5). Found by compat-min: before the fix
   `✘ the app script is loaded as a module — no app.js tag` (`Passed: 34  Failed: 1`). Fix: new
   `Assets::adminPrintsScriptModules()` (the API exists and WordPress hooks `print_enqueued_script_modules` to
   `admin_print_footer_scripts`); otherwise the existing classic enqueue with a `type="module"` tag is used. After:
   compat-min 35/35 (`<script type="module" src=".../assets/js/app.js?ver=1.0.0" …>`), and on WordPress 7.1.4 the
   new integration step (fix 5) shows the module path with the import map is still used.
4. **Integration: `tests/integration/run.php:85-88, 601-620`** — a final check that always runs (also with
   `LGA_IT_ONLY`): the run added no "PHP Deprecated/Warning/Notice/Fatal error/Parse error" line from a plugin file
   (`includes/`, the main file, `uninstall.php`, by the plugin folder's symlinked and real path) to the site's
   `WP_DEBUG_LOG`. Before it, the first PHP 8.5 run passed (`Passed: 533  Failed: 0`) while it logged fix 2's 12 lines. Evidence: in a throwaway copy with the
   old `Backlinks.php` (the site's plugin symlink pointed at the copy inside the flock and restored after),
   `LGA_COEXISTENCE=0`, PHP 8.5: `Passed: 497  Failed: 1` with the two Backlinks lines in the failure detail; the
   repository on both PHP versions: passes.
5. **Integration: `tests/integration/run.php:517-543`** — step "Admin dashboard page loads the app" (3 checks): the
   owner's dashboard page over HTTP (200, SPA root), `Assets::adminPrintsScriptModules()` on this WordPress, the
   import map and `app.js` as a script module. Guards fix 3's 6.6+ branch.
6. **Unit: `phpunit.xml.dist:7, 9`** — `failOnDeprecation="true"` and `displayDetailsOnTestsThatTriggerDeprecations`
   (§12.3, §12.6). Before, a deprecation from plugin code inside a test ended `OK, but there were issues!` with exit 0
   (probe on PHP 8.5 with the HEAD config); after, exit 1 on both versions. `failOnWarning` still fails a warning
   (probe: exit 1). Probes in `S/wp12p2/mut`, deleted afterwards.
7. **Unit: `tests/bootstrap.php:13-30, 381-382`** — a handler for the bootstrap itself: a deprecation raised from a
   plugin file while the bootstrap runs becomes an `ErrorException` ("Error in bootstrap script", exit 2, probe). It is
   removed at the end of the bootstrap: PHPUnit 11 installs its own error handler per test only when no other handler
   is registered (`ErrorHandler::enable()`), so a handler left in place would switch off PHPUnit's warning and
   deprecation handling. A first version that stayed registered was caught by the probes (in-test deprecations
   became errors, PHPUnit's handler was not active) and replaced before any run reported here.

No change silences anything: no `@`, no `error_reporting()` change. The two `@file_get_contents()` of the staged

## 6. Deviations from the design, with reasons

1. **Four files instead of two** (part 1): the rules of `php85-scan.sh` are a PHP file behind the shell script, and
   both scans share `bin/scan-lib.php`.
2. **Token-aware instead of grep-based** (§11.8 says "grep-based"; part 1): comments, strings and inline HTML never
   match (a plain grep flags ~80 backtick lines of comments and SQL in `includes/`), an enum `case X;` is told apart
   from a switch `case X;`, a return type from a ternary `) : null;`.
3. **A stand-in WordPress source** for the compat-api unit test, so the "@since 6.6" detection is proven on every unit
   run; the real-source test needs `LGA_WP_PATH` and is skipped with the reason without it (3 skips in the default
   unit command instead of 2).
4. **The bootstrap does not convert deprecations raised inside data providers.** PHPUnit 11 handles errors only
   during a test and refuses to install its handler while another one exists, so the bootstrap handler must be gone
   before the tests start (fix 7). A deprecation in a data provider is printed by PHP and the run still passes (probe:
   exit 0, "Deprecated: …" in the output). The unit runs above contain no "Deprecated" or "Warning:" line. Closing
   this needs a PHPUnit extension (subscribers on `DataProviderMethodCalled`/`Finished`); not done in WP12.
5. **compat-min without the wizard** (WP27), see §5.

## 7. Observations for later packages (not changed)

- **Weekly backlink trend on SQLite:** the SQLite translation used on the test sites maps `%x`/`%v` of
  `DATE_FORMAT` to strftime codes that give NULL, so `Backlinks::weeklyTrend()` is all zeros on the LGA site (MySQL
  computes it). The analytics package could compute weeks portably (in PHP, or from `YEARWEEK`-free SQL).
- **Error-swallowing wrappers:** `Support\ServerResources::quietly()` and `Support\Opcache::status()` install
  `set_error_handler( fn() => true )` around their reads (open_basedir and `opcache.restrict_api` warnings). Such a
  handler would hide a deprecation raised inside as well; today they wrap `is_readable`, `file_get_contents` and
  `opcache_get_status`, which raise none on PHP 8.5.
- **compat-api "unknown" symbols (8, listed, not failed):** `as_enqueue_async_action`, `as_next_scheduled_action`,
  `as_schedule_recurring_action` and `as_unschedule_all_actions` (no `@since` in Action Scheduler's `functions.php`;
  part 1 found all four in the 3.6.1 package of WooCommerce 8.0.5), the `cli_init` hook (WP-CLI's, not in the
  WordPress source), `fpm_get_status()` (PHP-FPM), `pll_get_post_language()` (behind `function_exists()`) and the
  `wpml_post_language_details` filter (multilingual plugins).
- **The WordPress 6.5 dashboard loads its modules without the import map**, so the relative imports there are not
  versioned (cache busting after an update relies on the browser revalidating); 6.6+ keeps the versioned import map.
- WP31 reruns all of this; the same runners work unchanged (`S/wp12p2/it.sh <php> <out>` is the helper used here).
