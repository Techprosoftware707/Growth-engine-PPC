# Operations guide

## The automated cycle

Every tick (default every 5 minutes via Action Scheduler) the pipeline enqueues the stages that are due and runs queued jobs within the time budget:

1. **Discover** (daily) — seeds (once), rotating search queries, competitor backlinks (weekly), brand mentions (weekly).
2. **Evaluate** (continuous) — profile, relevance, risk, provider metrics, score. Rejects poor sites, qualifies the rest, finds the submission page and contacts. Each run takes prospects in this order: first those that did not come from the verified opportunity import (new discoveries, then due re-reviews, oldest first, then automatic re-checks of sites that were unreachable or hit an evaluation error), then imported prospects in the same order. Imported prospects are still evaluated, only after the others, so the import cannot hold up newly found sites under the daily evaluation limit. A site that was already a prospect before the import counts as a discovered prospect, not an imported one.
3. **Find opportunities** — one opportunity per qualified prospect at the real submission/contact page; broken links on resource pages.
4. **Package** (hourly) — complete submission packages for opportunities at or above `min_score_auto_queue`.
5. **Submit** — processes queued packages. In the default auto mode a package queues itself when the site scores ≥ the quality threshold and every structural gate passes; in stricter modes it waits for your approval unless the site is set to *Always allow*. A site set to *Never automate* always gets its package prepared for a person. Whatever cannot be automated safely waits in the review queue.
6. **Verify listings** (every 6 h) — checks submitted listings; confirmed listings become backlinks and the prospect becomes *acquired*.
7. **Auto outreach** (daily) — drafts personalised messages for qualified editorial prospects (resource pages, publications, broken links, unlinked mentions, podcasts, associations) into evergreen "Auto" campaigns (a paused, archived or completed Auto campaign gets no new drafts), fills the campaigns you created with matching prospects, and approves what may be approved automatically right now (under Autopilot: every waiting first-contact draft); **Outreach send** delivers approved messages inside the send window and limits (auto-drafts are approved automatically only with *Outreach autosend* on and *Require individual approval* off); **Follow-ups** (daily) drafts follow-ups for unanswered messages, which are queued to send without review only with autosend on and in campaigns set to auto-approve follow-ups.
8. **Monitor backlinks** — checks due links, records changes, raises notifications; **Import backlinks** (weekly) pulls provider and GA4 referral data.
9. **Cleanup** (daily) and **Metrics refresh** (weekly).
10. **Storefront audit** (daily, and again after products, product categories or tags, or menus change) — see *Storefront compliance check* below.
11. **Import verified** (when the bundled `data/verified-opportunities.json` changes) — imports the researched opportunities as owner tasks.
12. **Site audit** (daily), **IndexNow** (hourly, only when URLs are waiting and the site may submit) and **Internal links** (weekly, suggestions only; daily while automatic links are on, see [Autopilot](#autopilot)) — see the On-site SEO page.

Every automated action is written to the audit log (Logs → Audit).

## Server pressure

From 1.2.4 the plugin never adds background work while the server is struggling. On the live store a plugin update left PHP's code cache (OPcache) full while an UpdraftPlus backup held PHP-FPM workers for minutes; the plugin's tick kept taking another worker for up to 20 seconds every 5 minutes and the store answered 504 for about 20 minutes.

**When background work pauses.** Before each tick (and before a kick or a Grow now step) the plugin asks `Automation\LoadGuard`, which checks, without any HTTP request:

| Reason | How it is detected | Dashboard text |
|---|---|---|
| PHP's code cache is restarting | `opcache_get_status(false)` reports `restart_pending` or `restart_in_progress` (a warning from `opcache.restrict_api` or a missing function counts as "nothing known") | Paused: PHP's code cache is restarting (resumes automatically). |
| A backup is running | UpdraftPlus: a `updraft_backup_resume` event (every running UpdraftPlus backup keeps its next resumption scheduled) or a "Backup now" event (`updraft_backupnow_backup*`) in the cron array, due within the next 30 minutes or overdue by less than an hour, unless that backup's own record `updraft_jobdata_<nonce>` says `finished`. The cron array is an autoloaded option, so this costs no database query; the job record is read only when such an event exists, and other options are never scanned. Other backup plugins report through the `ppclg_backup_running` filter (return `true` or the plugin's name). | Paused: a backup is running (resumes automatically). |
| The plugin was just updated or activated | The first request that runs a new `PPCLG_VERSION` (or the activation) stores `ppclg_running_version` with the time; for 10 minutes after that OPcache can warm up and other plugins finish their own post-update work. | Paused: the plugin was just updated (resumes automatically in about N minutes). |
| The site owner or host says so | `add_filter( 'ppclg_pause_background', … )`: return `true` or a short message to pause, `false` to let the work run even when a reason above was found. | Paused: *your message*. |

The answer is kept for the rest of the request; every tick asks afresh.

**What a pause does.** The tick (also *Run tick now* on the Automation page) returns at once with `skipped_reason: paused`: no job is claimed, no stage is enqueued, no growth step runs, no limit is spent and no stage's cadence is used up. *Kick scheduler* starts nothing (its answer says why). A Grow now run waits instead of failing: `POST /growth/step` answers `waiting: true` with the text above, `paused` and `retry_after: 60`, and the panel asks again about once a minute instead of every 3 seconds. *Run now* on a single stage still runs it (you asked for it), and its answer carries the warning. Outreach keeps its send window and daily limits; nothing is lost, only delayed. The first check that finds no reason resumes everything. Each pause is written to Logs → Automation once when it starts and once when it ends ("Background work resumed after 12 minutes (a backup is running)."), and the Overview's Automation card and the Automation page show it while it lasts (`paused` in `GET /automation/status` and `GET /overview` → `automation`).

**A full OPcache does not pause anything.** That state can last for months; pausing on it would stop Autopilot for good. Instead Tools → Site Health shows the test "PHP's code cache (OPcache) is full" (critical: OPcache reports `cache_full`, less than 5% of its memory is free, or the interned strings buffer is full) or "… is almost full" (recommended: more than 90% of the memory or of the interned strings buffer in use), with the numbers and the fix. While it is critical the Overview shows the same notice (`opcache` in `GET /overview`). When PHP does not let plugins read the status the test passes with "nothing to report".

**Recommended OPcache sizes** for a WooCommerce store with this plugin and a backup plugin. In the `php.ini` (or a file in the `conf.d` folder) that **PHP-FPM** uses (not the CLI one), set:

```ini
opcache.memory_consumption=256
opcache.interned_strings_buffer=32
opcache.max_accelerated_files=32531
```

then restart PHP-FPM (for example `systemctl restart php8.5-fpm`). On managed hosting, ask your host to make this change. Every plugin update leaves the replaced code in the cache as wasted memory until OPcache restarts, so a cache sized with room to spare is what keeps updates from slowing the store.

## Campaigns: what happens after "Create campaign"

Creating a campaign (Outreach → New campaign) builds its drafts straight away, for every eligible prospect whose best opportunity fits the approach: qualified, approved or in-progress websites with an active, conspicuously published contact, not on the suppression list, not contacted within the cool-down (`outreach.min_days_between_contacts`), without an open message in another campaign (one open message per website) and not a verified-database owner task. Unsent drafts that an "Auto:" campaign holds for the same approach move into your campaign. The toast says how many drafts were made; anything that did not fit the 15-second request continues in the background.

Each campaign card has a **What happens next** line, for example:

- *Waiting for your approval: approve the campaign and its 3 drafts so the engine can send them.* (with **Approve all drafts** and *Open the drafts*)
- *Sending automatically: 2 of 5 today; next send window Monday 09:00 Toronto time.*
- *Paused: the sender email domain cannot receive mail. Fix it under Settings → Outreach; nothing is sent until then.*
- *No qualified prospects with a published email address for resource page inclusion yet; the engine adds them as it evaluates sites.*

**Build drafts** lists only the prospects that match the campaign's approach and can be written to; switch on *Show all qualified prospects* to pick others. A skipped prospect says why (for example "This website already has an open message (draft #12 in campaign "Auto: Industry partnership")").

## Autopilot

**Overview → Grow your site → Autopilot** (also on the Automation page) is the one switch for running without approvals. Switching it on shows the policy text and the hard limits and asks you to confirm; the consent is stored (user, time, policy version) and written to the audit log, and the background automation master switch is turned on. The policy text is versioned (`1.2.2-1` since 1.2.2, which added saving a page as your account and taking automatic links back out, see [Automatic links only where visitors see them](#automatic-links-only-where-visitors-see-them)); a consent given under an earlier version keeps everything else running, and the Autopilot card says when switching it off and on again would give the new one. While it is on:

- Drafts in every campaign (yours and the "Auto:" ones) and the campaigns themselves are approved automatically ("system:autopilot" in the audit log), drafts that were already waiting are approved at once, and the send stage mails them inside the daily and weekly email limits, each campaign's daily limit and the send window. Unreviewed first-contact email goes only to sites scoring at or above `min_score_auto_queue` (the same bar as the "Auto:" campaigns): your campaigns are filled with those sites only, and a draft to a lower-scoring site (built before Autopilot or by you) waits for you, which the card and *Needs you* say.
- Approval waits for a sender that is ready (a complete identity and a sender / Reply-To domain with an MX record). A draft that could not be approved for a reason that clears by itself (the sender, the contact cool-down) is marked "Waiting to approve: …" and approved automatically once it clears; fixing the sender in Settings approves the waiting campaigns and drafts at once.
- A draft built before you changed the postal address or the brand gets the current footer at approval (see [The compliance footer follows Settings](#the-compliance-footer-follows-settings)), so it is approved instead of being refused. Drafts that 1.2.0 marked "Not approved: Body must contain the sender postal address." (or "… the unsubscribe link.") count as waiting, not as needing an edit, and are approved on the next run, when Autopilot is switched on, or at once when you save the address or brand in Settings. Without Autopilot the same happens in the "Auto:" campaigns when *Outreach autosend* is on and *Require individual approval* is off. A draft whose edited footer cannot be updated counts as needing an edit instead.
- Automated submissions run in **auto** mode (the Automation → Submissions switch and the submission mode are overridden); every structural gate still applies (public listing form, no CAPTCHA or login, robots.txt, per-site *Never automate*, limits, storefront gate, no duplicates, no paid boxes). Packages that were waiting for review are re-checked on every packaging run and queued once they pass; the ones that still do not (below the auto-queue score, *Never automate*) stay in *Pending review* and *Needs you* lists them.
- Follow-ups are sent automatically only when reply tracking is set up (Settings → Integrations → Email, RDAP & inbound replies → inbound webhook secret). Without it the engine could follow up someone who already replied, so follow-ups stay drafts and the card and *Needs you* say so; once reply tracking is set up, the follow-up drafts that waited are approved and sent too.
- Drafts the claims filter flags stay drafts ("needs editing"); Grow now lists them as your only outreach action.
- Sites that need an account, login, CAPTCHA, phone call or a paid plan stay owner tasks; hand them to a *Link Growth Submitter*.
- **Internal links** are added automatically: the internal_links job runs daily and applies the pending suggestions with the highest relevance first, up to *Automatic internal links per day* (`seo.auto_apply_per_day`, default 20) and never more than *Suggested links per item* per page. Each change goes through the same checks as an Apply click (no links in headings, existing links, opaque blocks) and WordPress keeps a revision of the previous content first; the audit log records the actor "system:autopilot". A suggestion the checks refuse stays in the list for you (**Left for you** on the On-site SEO page, with the reason) and is not retried (also not after the list is regenerated, while the text at that spot is unchanged); the daily summary counts those separately from suggestions that were closed as no longer valid. See [Automatic links only where visitors see them](#automatic-links-only-where-visitors-see-them) for the page check and for pages with inline SVG or JSON-LD. **On-site SEO → Undo automatic links** (asks first) removes every automatic link still present: a page not edited since gets exactly its earlier content back, an edited page loses only the inserted link; undone links are not added again. The same automatic links can be switched on without Autopilot (Settings → Automation → On-site SEO → *Add the best internal links automatically*).
- **Competitors are found automatically** while Settings → Discovery lists none and SE Ranking is configured: at most once every 30 days (one provider lookup, within the daily *Provider lookups* limit) the engine asks SE Ranking for your competitors and keeps real ones only — marketplaces, social networks, encyclopedias, news, government, your own domain and any domain whose name reads as health, medical or pharmacy are left out. They are listed under *Found automatically by Autopilot* in Settings → Discovery, apart from your own list; remove any you do not want (a removed domain is never added back). Their backlink profiles are mined weekly for prospects, so discovery works even without a search key; each competitor is one provider lookup and counts against the daily *Provider lookups* limit (the scan continues the next day when the limit is reached); the discover step says what it found.
- The **Grow your site** panel says "Autopilot is on — nothing needs your approval", its step labels drop "for your approval" / "applied only by you", and *Needs you* lists only what Autopilot cannot do for you: a sender email that cannot receive mail or an incomplete sender identity, no discovery source (it names the one key that unlocks it), provider credits used up, background automation switched off, the storefront gate, drafts the claims filter or a compliance check flagged, follow-up drafts waiting for reply tracking, drafts to sites below the auto-queue score, listing packages Autopilot does not submit by itself, and owner tasks for sites that need an account (with the Submitter-role hint). When Autopilot is switched on or off after a run, the panel's tiles follow the switch at once and *Needs you* says that it is from the earlier run.

Switching it off stops automatic sending at once: messages Autopilot approved but did not send yet return to draft (also any that a background run already in progress approved afterwards: the send stage re-reads the switch and returns them before it sends anything) (marked "Returned to draft: Autopilot was switched off …"); messages you approved yourself stay approved. The individual settings (*Outreach autosend*, *Require individual approval*, *Automated submissions*, submission mode) then apply exactly as before. `POST /settings` cannot switch Autopilot on without `confirm=true`, and the consent record cannot be written through it.

## The compliance footer follows Settings

Every outreach email ends with the CASL / CAN-SPAM footer: a line with the brand and the postal address (`site.brand_name`, and `outreach.postal_address` or, when that is empty, the business address under Settings → Site), then "If you'd rather not hear from us again, reply with "unsubscribe" or use this link: …". It is written into a draft when the draft is built. When you change the address or the brand later, the footer of every message that is not sent yet (draft, approved, scheduled, failed or rejected) is rebuilt from Settings before it is approved (by you or by automation), before it is sent, and when you save an edit:

- The footer carries the postal address exactly as configured, however long, on one line (a line break in the address becomes ", "): it is the same text the postal address check looks for, so a refreshed footer always passes it.
- Only the footer block is replaced, in place; the rest of the email stays exactly as it was and the unsubscribe link keeps its token. The block runs from the "<brand> · <address>" line, through the lines its address continues on (an address written on several lines, or one you wrapped) and any blank lines you added above the unsubscribe line, to the unsubscribe line; it is replaced whole, so no line of the old address is left. Earlier copies of the footer for the same message (an edit saved by 1.2.0 added a second footer under the stale one) are removed, so one footer remains.
- A message without a footer gets the current one appended; a deleted unsubscribe line or a deleted "<brand> · <address>" line is put back in its place. A footer you wrote yourself that already carries the current address and the unsubscribe link is left alone. The footer line is generated from Settings: to change what it says, change the brand or address there rather than in the draft (an edited footer line that keeps the "·" between brand and address is replaced at the next save, approval or send).
- A footer edited so that it cannot be recognised any more (the line above the unsubscribe line is no longer a "<brand> · <address>" line, for example with the "·" replaced, or the link sits in your own wording without the current address) is not guessed at, because that line may still hold the old address. The save says so, and approval and sending refuse the message with "… The footer was edited, so it could not be updated to the current postal address …": the draft counts as needing an edit and automation does not retry it. Delete the edited footer lines (the current footer is then added) or type the current address into them, and save.
- Sent, replied, closed, opted-out and bounced messages are never changed; they keep the footer they were sent with.
- Each rewrite at approval or send is recorded in Logs → Audit as `outreach.footer_refreshed` (actor `user:N` when your approval led to it, `system:outreach` for automation). A manual save records no separate entry: its `outreach.message_updated` entry has `footer_refreshed: true`.
- The refresh approves nothing itself. Drafts are approved automatically only where automation already approves drafts: under Autopilot, or in the "Auto:" campaigns with *Outreach autosend* on and *Require individual approval* off. Otherwise they keep waiting for you.

## Send window and time zone

The send window (Settings → Outreach, default 9–17 Monday–Friday) is evaluated in `outreach.timezone` when it is set to an IANA zone. Left empty, the WordPress time zone is used, except when WordPress is on UTC and the business country is Canada: then the province under Settings → Business decides (ON/QC/NU Toronto, MB Winnipeg, SK Regina, AB/NT Edmonton, BC/YT Vancouver, NS/PE/NB Halifax, NL St. John's). The Outreach page shows the effective zone and the next window ("Next: Monday 09:00 Toronto time").

## Grow now (one click)

**Overview → Grow your site → Grow now** runs every stage above once, in this order: check the storefront and the setup, import verified opportunities, audit on-site SEO, notify search engines (IndexNow), suggest internal links, discover, find unlinked mentions, find broken-link opportunities, evaluate, find opportunities, prepare packages, submit, verify listings, draft outreach, check backlinks, import backlinks, refresh metrics, summarise.

- The panel lists each step with its status (done, skipped, blocked, failed) and one sentence about what it did. The browser asks the server to continue every few seconds; each request works for at most `growth.step_seconds` (20 s).
- If you close the tab, the scheduler continues the run about a minute later, even while the automation switch is off (the run was your explicit click). While other jobs are due (sends, follow-ups, monitoring), background ticks alternate between the run and the queue so neither starves. Opening the Overview again resumes the display. Only one run is active at a time; *Stop* keeps what was done, cancels the run's queued follow-up jobs, and a job of the run that is already running finishes its current batch without continuing. *Stop* stays available when the panel loses contact with the server (the run keeps running on the server until stopped).
- The run uses the same gates as the scheduled stages: the submission policy (including the storefront gate), robots.txt, the daily limits and the outreach approval rules. Steps run as manual runs, so a stage whose own switch is off still runs, but *Automated submissions* and *Outreach autosend* are always respected. The submit step shows **blocked** when the storefront check blocks or automated submissions are off.
- The run never changes a setting and never edits your pages, except automatic internal links while Autopilot (or *Add the best internal links automatically*) is on; otherwise internal links are suggestions. What it may send on its own follows your settings, and the panel's subtitle states it: with *Automated submissions* on in **auto** mode, listings to sites that pass every safety gate are submitted automatically; outreach is only drafted, and emails go out after your approval (or automatically while *Outreach autosend* is on and *Require individual approval* is off). IndexNow is notified of new and changed pages.
- At the end, **What happened** shows headline numbers (prospects, owner tasks, drafts awaiting approval, live and lost backlinks, SEO issues, IndexNow submissions, link suggestions, storefront status) and **Needs you** links to the pages where you act. A number that could not be read shows as "not available", never as 0; SEO issues show "not run yet" until an audit has finished a pass, and "(partial)" while one is in progress.
- Work that does not fit (for example more prospects than the evaluation rounds allow) continues in the background; the step says so.

## Storefront compliance check

Listings and outreach describe the business as a research-use-only supplier of laboratory reagents. When the storefront presents products for consumer use, every automated listing and email would misrepresent the business, so the plugin checks the store first:

- **What it reads**: product category and tag names, slugs and descriptions, published product titles and short descriptions, and menu items (page and post titles when WooCommerce is not active). It never edits anything.
- **Results**: *block* (consumer-use wording such as weight loss, anti-aging, tanning, skincare, beauty, nasal spray, capsules, injections, syringes, needles, dosing, supplements, wellness, "for human use", or a product title that is a consumer dosage form), *warn* (wording to review: recovery, growth, cognitive, metabolic, longevity, healing) or *pass*. Each finding names the term, where it is and a link to edit it.
- **While it blocks** (and the gate is on): new packages become owner tasks under Submissions → Needs manual, queued submissions are moved there when the queue runs, and outreach sending pauses; each paused message shows "Paused: the storefront compliance check is blocking …". Drafting and packaging continue so you can review them. These items do not return to the queue by themselves after the store is fixed: approve or retry them.
- **Your decision**: how the store presents itself is your legal decision, ideally with Canadian regulatory counsel. Either change the storefront wording (the check re-runs when products, categories, tags or menus are saved; *Re-check now* on the banner runs it at once), or click *Acknowledge* to record that you reviewed these exact findings. An acknowledgement lasts until the findings change. Turning the gate off (Settings → Outreach & compliance) asks for confirmation.
- **Fail closed**: if the check cannot run, automated submissions and outreach sending stay paused and the error is logged.

### Automatic links only where visitors see them

From 1.2.2, before the automation adds a link to a page or post it checks that the item's public page actually shows the item's text and the words around the anchor. A page can be published and still never print its own content: the static front page of a theme whose `front-page.php` is hard-coded (the live home page), the posts page (WordPress lists posts there), the WooCommerce shop when it shows only the product catalogue, or a page template that ignores the editor content. A link added there is invisible to visitors and Google.

- **No request needed**: the posts page (while the front page is a static page) and the WooCommerce cart, checkout and account pages are recognised from the settings (they show the visitor's own cart or account, and WooCommerce tells search engines not to index them, so a link there has no search value). The WooCommerce shop page is checked like any other page: classic themes print its content as the shop description above the products, so only its page can say whether the text is shown (body class `woocommerce-shop` names it); when it shows only the catalogue its rows say so ("this is the WooCommerce shop page …"). An item that no longer exists or is not published is never requested: a deleted item's suggestions and automatic links are closed as no longer valid ("Closed: the item no longer exists."), an unpublished item's suggestions are closed as an *Apply* click would close them, and its automatic links are left alone until it is published again.
- **Everything else**: the engine requests the item's address once, as an anonymous visitor (no cookies, no redirects followed, `Accept: text/html`, never `text/markdown`, an 8-second timeout, at most 3 pages per run and per PHP request — a *Grow now* step or a cron tick asks for at most 3 pages in all — 2 seconds apart, within the job's time budget). The answer counts only when it is HTTP 200 HTML whose `<body>` names the item (body class `page-id-N` / `postid-N`, or the item's shortlink or canonical address), so a login wall, maintenance page or security challenge is never taken for the page. A few sentences of the item and, for each suggestion, the anchor with up to six words on each side must appear as consecutive words in the visible text of the page (scripts, styles, SVG, comments and `<head>` ignored; quotes, dashes and entities compared alike). An anchor alone never counts: it also appears in menus.
- **Posts split into pages** (a page break, `<!--nextpage-->`): the item's address shows its first page only, so only the first page is compared. A suggestion on page 2 or later is left for you (**Left for you**: "these words are on a later page of this item …") instead of being set aside, also when the first page holds too little text to compare (that page is then not reported as "could not be checked"), and text on later pages never counts as evidence that the page hides its content.
- **Not shown**: the item's suggestions move to **Not shown on the page** with the reason ("Not added: this page's template doesn't display its content, so visitors and Google wouldn't see the link."); they are not added automatically and not counted as waiting. An automatic link already on such an item is taken back out the same way *Undo automatic links* does it (exactly the earlier content when the item was not edited since, otherwise only the `<a>`; a revision first; audit `seo.internal_link_auto_removed`, actor "system:autopilot"), and marked "Removed automatically …". An automatic link that is no longer in the item because someone removed it in the editor is not counted or audited as removed: it is closed under *Dismissed* ("Closed: this automatic link is no longer in the item …") and, as before 1.2.2, never suggested or added again. A suggestion whose page shows the item but not those words is set aside the same way ("these words aren't on the page visitors see").
- **Unknown**: a network error, a timeout, an answer other than 200, a page that does not name the item, too little text to compare, or the item's words shown without the bold or italic formatting the item gives them (a plain-text excerpt or summary, where a link would not show either) decides nothing: the item is skipped for this run and checked again after about 6 hours (its rows say "Not checked yet: …"). A timeout, HTTP 429 or 5xx, a security challenge or an answer slower than 5 seconds also stops further page requests for the rest of the run and pauses page checks for 10 minutes in every later run and request (transient `ppclg_render_check_pause`; the job summary says "page checks are paused for a few minutes …"), so a busy host is not asked again right away by the next round, another *Grow now* click or the cron. No continuation is queued for a paused run; the next scheduled run carries on.
- **Checked again** when the item is edited, its page template changes, the theme or its version changes, or it becomes (or stops being) the front page, the posts page or a WooCommerce page, and in any case after 7 days. When a page starts showing its content again, its set-aside suggestions return to the queue (and removed links are added again).
- **By hand**: *Apply* still works on any of these rows; the result says when the page is known not to show its content ("visitors and Google won't see this link").
- **Pages with inline SVG or JSON-LD** (most long-form articles): background saves run without a logged-in user, so WordPress would strip `<svg>` and `<script type="application/ld+json">` on save, and 1.2.1 left these links for you ("WordPress would re-filter other markup"). From 1.2.2 such a save is made as the administrator who switched Autopilot on (the consent record, and only a consent given under the 1.2.2 Autopilot text, which says so: policy `1.2.2-1`; a consent from 1.2.0 or 1.2.1 keeps the rest of Autopilot running but not this, so switch Autopilot off and on again once after the update). While Autopilot is off it is made as the user who switched *Add the best internal links automatically* on (recorded in `ppclg_auto_links_consent` only when that setting is switched on with its confirmation, which says so and which the settings page asks for also while Autopilot is on, and deleted when it is switched off, so a consent that was taken back never comes back). It is for that one save only, and only while that user still exists, may edit the item and may save unfiltered HTML (on multisite only a super admin; never with `DISALLOW_UNFILTERED_HTML`). The current user is restored right after, the revision is credited to that user, and the audit entry keeps "system:autopilot" as the actor with `saved_as`. Only the link is added; every other byte stays as the administrator saved it. When no such user qualifies, the refusal stays as before. Refusals stored by 1.2.1 are tried again automatically once a user qualifies.
- **More than one round a day**: when a run stops for time or for the page limit while links are left for the day, the internal_links job runs again 15 minutes later without refreshing the suggestions. A *Grow now* step never runs that waiting round early (it leaves it to the scheduler and says more work remains) and does not chain one itself.
- **Limitation — excerpts**: the check compares words, and an automatic link only shows where the page prints the item's content. A template that prints a plain-text excerpt is recognised only when the item has bold or italic phrases (`<strong>`, `<b>`, `<em>`, `<i>`, two words or more) among the words the excerpt shows: those must appear with their formatting. When none of the item's formatted phrases is in the excerpt, or the item has none, such a page still passes as showing the content. A stricter rule (for example requiring the plugin's own `<a>` on the page) is not used because page caches (Cloudflare, page-cache plugins) can serve a copy from before the latest edit, which would make visible links look missing and take them out; for the same reason a missing formatting never removes a link or sets a suggestion aside, it only leaves the page unchecked until a later run. No page of the live theme prints an excerpt in place of its content.

### Internal links: never the brand name, never another language

From 1.2.3 two rules apply to every internal-link suggestion and every automatic link. They come from the live site, where the English Terms of Service page got "Pure Peptides Canada" linked to the French About page and "Peptides Canada" (the end of the brand name in "belong to Pure Peptides Canada or its licensors") linked to the home page.

- **The brand is never link text.** The brand is *Brand name* and *Legal name* (Settings → Business profile), every line of *Brand terms for mention scans* (Settings → Discovery), the WordPress site title and the site domain with and without its ending (`purepeptidescanada.com` and `purepeptidescanada`). They are compared without capitals, extra spaces, punctuation or accents, so "PURE PEPTIDES CANADA", "pure-peptides canadá" and "PurePeptidesCanada.com" are all the brand. A target whose anchor is the brand or consecutive words of it ("Peptides Canada", "Pure Peptides", "Pure") is not linked by those words; a piece of a word is not enough ("scan" is not the brand). To add a spelling (for example a French form of the name), add it to *Brand terms for mention scans* (it is also searched for as a mention of the brand on other sites).
- **Focus keywords**: a page is a target by its first Rank Math focus keyword. When that keyword is the brand, the page is a target by its next focus keyword that is usable (not generic, not the brand) instead, so the French About page ("pure peptides canada, fournisseur canadien de peptides, …") is linked by "fournisseur canadien de peptides", from French pages only. The fallback is only for a brand first keyword: the first keyword is the one the owner chose for the page, and a page whose first keyword is generic ("home", "contact") or too short stays out as before. A page whose keywords are all the brand ("peptides canada" on the home page) is no target.
- **Words inside the brand name are never linked.** Where the brand is written in a page (whole words, any capitals or accents, also without spaces), no link starts or ends inside it: "Peptides Canada Express" in "Pure Peptides Canada Express" is skipped and the next mention outside the name is used. A link that holds the whole name and more ("Pure Peptides Canada reviews") is allowed. The page check before an automatic link reads the words around that same spot.
- **A page links only to pages in its own language.** The language of an item is, in this order: what Polylang says, what WPML says (`wpml_post_language_details`), the filter `ppclg_post_language` (post id → language code, `''` when it does not know), for the site's own French pages (post meta `ppc_en_counterpart`, set by the ppc-french plugin) the language their address starts with (`/fr/…` → French; one without such a start is treated as an unknown language that matches no other page), a two-letter language code at the start of the address below the home address (only ISO 639-1 codes: `/fr/`, `/es/`, but not `/go/`), the language the item's text is written in, and otherwise the site language (*Settings → General → Site Language*). The text (title, excerpt and content) is read on an English or French site, for English and French only: an item is in the other language when its text clearly reads as it — at least 8 common short words of that language ("le", "les", "nous", "avec", … / "the", "and", "with", …), 4 of them different, and three times as many as of the other language. That is how the French pages at the site root (`/acheter-peptides-canada/`, `/peptides-recherche-quebec/`), which have neither a `/fr/` address nor (as far as is known) `ppc_en_counterpart`, are French: they are offered French targets only, are no target for English pages and are offered to the French pages under `/fr/`. A short or mixed text (an English page quoting a French phrase) keeps the site language, and a French page with `ppc_en_counterpart` but no `/fr/` address is French by its text too (otherwise unknown). A page in another language that is not detected (Spanish, or too little text) can be named with `ppclg_post_language` (docs/EXTENDING.md). Each item's language is worked out once per run. Two targets with the same anchor in different languages (an English and a French product with the same title) are no longer dropped as ambiguous: each language links to its own.
- **Suggestions made before 1.2.3**: a waiting suggestion (or one set aside under *Not shown on the page*) that breaks a rule is closed under **No longer valid** on the next suggestion run (weekly, daily under automatic links, or *Find suggestions*) and on the next automatic run, with the reason: "Not suggested: the link text is your brand name." or "Not suggested: the target page is in another language." (stored as `closed_rule` `brand` or `language`; a language closure also keeps `source_language` and `target_language`). It is never added automatically, and *Apply* closes it the same way instead of linking. Links already applied are left as they are, because a person may have chosen them (remove one in the editor, or with *Undo automatic links* for automatic ones); dismissed and undone suggestions stay as they were. A suggestion run in progress during the update starts again under the new rules.

## On-site SEO page

- **Site audit**: issues by severity (high, medium, low) with the fix and an edit link. *Run audit* continues where the last batch stopped; the audit reads the database and changes nothing.
- **IndexNow**: the key file link, the last submission and its HTTP status, URLs waiting, and *Submit now* (compares every public URL now). Submissions happen only on the production site and never while WordPress discourages search engines. HTTP 403 means IndexNow could not read the key file: open the key file link and check that it shows only the key (a caching or security rule may block it). After any refusal the scheduled submission waits at least an hour; after HTTP 429 ("slow down") it waits as long as IndexNow's Retry-After asks (at most a week), and *Submit now* is disabled until then.
- **Internal-link suggestions**: listed 50 at a time (*Previous* / *Next*; `GET /seo/links` takes `per_page` 1–500 and `page`, and reports `total`, `pages`, `page`, `per_page`). The filters are *Waiting* (pending), *Left for you* (pending suggestions the automation could not add by itself, `status=refused`, each with its reason), *Not shown on the page* (`status=not_shown`, see above), *Applied*, *Dismissed* and *No longer valid*. Each row shows the sentence, the anchor and the target. *Apply* (or *Apply all* / *Apply these N* for the rows on the page, after confirmation) first makes sure the current content is kept as a revision (the restore point), then adds the link; nothing is changed if the text was edited since the suggestion was made, or if WordPress keeps fewer than 2 revisions for the item. Text inside links and headings (also when written as `<a href=/x/>` or `<h2 />`) and inside blocks that render from their settings (for example Rank Math FAQ and HowTo) is never linked, nor is the brand name or a page in another language (see [Internal links: never the brand name, never another language](#internal-links-never-the-brand-name-never-another-language)); *No longer valid* lists the suggestions closed for those reasons with the note. *Dismiss* hides a suggestion for good.

## Verified opportunities (owner tasks)

The plugin bundles 595 researched opportunities (business directories, associations, research and data platforms, publications) with their submission pages, requirements and steps. They are imported once per data version as owner tasks: Submissions → **Owner tasks** lists them with tier, authority, kind (listing or outreach) and conditions. Each task has the listing kit (*Copy listing kit*), the steps, a safe link to the submission page and *Mark submitted* for the listing URL, after which listing verification takes over. The import contacts nobody and sends nothing; whether to pitch an outreach-type opportunity is your decision (automatic drafting skips them). Items whose domain is on the platform exclusion list (`data/excluded-domains.json`, for example Google Business Profile, LinkedIn or GitHub) are skipped and listed with the reason; allowing them means changing that exclusion list, which also lets discovery pick those platforms up. Items with no free tier (paid press releases, paid directory programs) are skipped as *paid_only*, because listings are free tiers only; a task created for one by an earlier import is closed. Items for a site where a listing was already submitted are skipped as *already_listed*, so no task asks for a duplicate listing. Automatic outreach drafting skips every prospect that has a verified owner task, whatever source first added the site.

## Handing owner tasks to a staff member or assistant

The plugin cannot do owner tasks for you: almost all of them need an account on the other site (590 of the 595 verified opportunities), and 52 also need a phone, postcard or ID check. Creating accounts automatically would break the rules the plugin follows (no account farms, no fake identities, no CAPTCHA tricks). What you can do is hand the queue to a real person.

1. Go to **Users → Add New** (Settings has a card with a link) and create a user for your staff member or assistant with the role **Link Growth Submitter**. Use their own name and email address.
2. They log in and see one menu item, **Link Submissions**: the open owner tasks (*To do*) and the ones they marked submitted in the last 14 days (*Marked submitted*).
3. For each task they open the submission page, create the listing with the listing kit (*Copy listing kit*), and click *Mark submitted* with the listing URL if they have it. Listing verification then checks that the link went live.
4. Personal-profile platforms need a real staff member who discloses that they work for the business; the listing kit says so on each task.

What the role can and cannot do:

- It has only two capabilities: `read` and `ppclg_submit_listings`. The plugin resets the role to exactly these two every hour, so a role editor cannot widen it by accident; for more access, use another role.
- It can list owner tasks (rows in *Needs manual*), read one, and mark one submitted. Tasks that need your decision stay with you and are not shown to it: the site is rejected, suppressed or on hold; the listing text fails the claims check; an earlier automated attempt may already have sent the listing; a listing on that site was already sent (a second one would be a duplicate); or the task is an outreach pitch to a person. When you open such a task, a note says why the submitter does not see it. It cannot approve, reject, retry or rebuild packages, edit package text, import the verified database, or open any other page or API route (prospects, contacts, outreach, settings, secrets, logs, backlinks, automation, growth, SEO, compliance). The server refuses those with 403 whatever the browser sends.
- What it sees of a task is the listing kit, the steps, the submission page and, for a detected form, the value to put in each field (hidden form tokens are left out): no adapter responses, error details or internal notes.
- The listing URL it enters must be on the site the task is for. A page on your own site is refused for everyone, because listing verification would count it as a link to you.
- Every *Mark submitted* is recorded in the audit log with that user's id (Logs → Audit, actor `user:<id>`).
- Nothing is emailed by this feature. Removing the user, or changing their role, removes access at once. Uninstalling the plugin removes the role and both plugin capabilities (the user accounts stay).

## Daily routine for the administrator (10–15 minutes)

1. **Overview** — read notifications (lost links, high-value prospects, replies), check that integrations are healthy and credits remain.
2. **Overview** — if the storefront compliance banner shows, read the findings and decide (change the wording, or acknowledge). Click *Grow now* when you want everything to run once and see what needs you.
3. **Submissions → Owner tasks / Needs manual** — (or let your staff member with the *Link Growth Submitter* role do this, see above) open each package, read the instructions, visit the submission page in your browser, paste the prepared fields and content, then click *Mark submitted* with the listing URL/confirmation. The verifier takes it from there.
4. **Submissions → Pending review** — approve packages whose destination you have authorised for automated posting (set its *Per-site automation* to *Always allow* in the prospect drawer first; approving re-checks every gate, and a package that still cannot be automated moves to *Needs manual* with the reason), or reject.
5. **Outreach → Messages → Draft** — read each draft, edit if needed (the claims check runs live), approve. Approved messages go out automatically within the send window, or use *Send now*.
6. **Prospects** — sanity-check new *qualified* prospects; hold, reject or suppress anything you do not want pursued. Rejections and suppressions are permanent for discovery, and they cancel the prospect's unsent outreach (draft, approved and scheduled messages). *Delete* also removes the prospect's opportunities, submissions, contacts and outreach messages, so it is refused once a submission or email was sent to the site: suppress or reject it instead.

## How automated submissions are authorised

In the default **auto** mode nothing is required from you: a site that scores at or above the quality threshold and passes every structural gate (public listing form, POST, no CAPTCHA, no login, no required upload, robots.txt allows the action URL, all required fields mappable, package text passes the claims filter, limits, no duplicate) is submitted automatically, and everything else lands in the review queue with a prepared package.

You can still steer it per destination with the prospect's **Per-site automation** setting (prospect drawer → Actions), which is *Inherit* by default:

1. **Boost**: set it to **Always allow** to authorise the site regardless of its score and of the submission mode (useful for moderate-scoring sites you trust, and only for directories whose terms permit automated listings). For directories that expose an official API, fill in the *Configured API* fields instead (endpoint, method, headers, JSON body template, success path, listing URL path, API key).
2. **Keep manual**: set it to **Never automate** and nothing is submitted to the site automatically in any mode, partner API included; its packages are prepared for you to submit by hand.
3. **Block**: suppress the prospect (or reject it) and the engine never touches it again.
4. **Slow down**: switch `automation.submission_mode` to `authorized_only` or `manual` in Settings → Automation, or lower the daily/weekly submission limits. Sites set to *Always allow* or with a partner API stay authorised in both modes; to stop all automated posting, turn off *Automated submissions*.

The engine re-checks every gate at send time and records the request and response.

The engine never solves CAPTCHAs, never logs in, never retries validation failures, never ticks fee or paid-placement boxes, and never posts comments, forum messages or profile links. It never re-posts a request whose outcome is unknown (a timeout or server error after the form was sent): that submission goes to *Needs manual* so you can check the destination first and use *Mark submitted* if the listing is there.

## Reading a score

Each prospect drawer shows the seven components with their weight, raw score, data source and notes. *Confidence* is the share of the 100 points backed by real data; without any metrics provider it is 70 (traffic and authority unknown). A high score with low confidence deserves a manual look before outreach.

## Handling replies and opt-outs

- Replies arriving through the inbound webhook mark the message *replied*, cancel the conversation's unsent follow-ups and raise a notification.
- A reply whose new text asks to stop ("unsubscribe", "opt out", "remove me", "stop emailing"…) opts the contact out and suppresses the address; quoted earlier messages and the plugin's own footer are ignored. Bounces mark the message and contact *bounced*.
- The unsubscribe link in every email opens a confirmation page; its *Unsubscribe* button, or the one-click unsubscribe of the recipient's mail client, suppresses the address immediately and cancels the contact's unsent messages. Merely opening the link changes nothing. The link keeps working as long as the sent message is stored (CASL requires at least 60 days).
- An opted-out contact cannot be set back to *active* in Outreach → Contacts. Only if the person asked to be contacted again, remove the entry under **Logs → Suppression list** first.
- Add domains or emails to **Logs → Suppression list** to stop any further contact or pursuit.

Common causes: sender identity incomplete, or the sender email on a domain without a mail server (the Outreach banner offers the site email), campaign not approved (or paused), message not approved, outside the send window (check the zone shown on the Outreach page), limits reached, WP Mail SMTP misconfigured.
