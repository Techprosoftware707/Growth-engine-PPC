# Testing

## Unit tests (no WordPress needed)

```bash
bash bin/lint.sh
bash bin/test.sh          # or: php bin/phpunit.phar
```

`tests/bootstrap.php` provides WordPress function stubs, an in-memory SQLite-backed `wpdb` replacement (`tests/Support/FakeWpdb.php`) that creates the plugin schema from the real dbDelta statements, and an HTTP fixture registry (`tests/Support/HttpFixtures.php`) that serves `tests/fixtures/sites/*` for `https://{domain}/…` URLs. Fixture sites: a Canadian laboratory directory with a listing form, a university resource page with broken links, a blog with linked/unlinked brand mentions, and a spam/PBN site.

1.2.0 Build B adds `tests/Unit/Seo/AutopilotLinksTest.php` (automatic internal links: most relevant first, daily cap, per-item limit, revision first, audit actor, kses refusals left for a person, undo restoring unedited items byte for byte and unlinking edited ones, off = suggestions only), `tests/Unit/Growth/AutopilotDiscoveryTest.php` (competitors found through SE Ranking with giants / media / government / health / own domain left out, 30-day interval, provider lookup limit, removed domains not re-added, the discover step summary, "Needs you" under Autopilot and the one-key discovery item) and `tests/Unit/Growth/AutopilotUiTest.php` with `AutopilotUiHarness.mjs` (headless Chrome: the Autopilot switch and its confirmation in the Grow panel, "Autopilot is on — nothing needs your approval", "Undo automatic links" on the On-site SEO page, and the automatic competitor list in Settings → Discovery; skipped when node, Playwright or a browser is missing).

1.2.1 adds `tests/Unit/Outreach/FooterRefreshTest.php` (the compliance footer follows Settings: a stale postal address, brand or Settings → Site fallback address is replaced in place with the rest of the body byte-identical and the token kept; a body without a recognisable footer gets one; a stale copy left above a current footer is removed; sent / replied / closed / opted-out / bounced / sending messages are never touched; drafts stuck with the 1.2.0 note "Not approved: Body must contain the sender postal address." count as waiting and are approved when Autopilot is switched on or the address is saved in Settings under Autopilot, without Autopilot only in "Auto:" campaigns with autosend on and individual approval off, never while individual approval is required; a manual save leaves a single footer; approved messages and follow-ups go out with the current footer; a postal address over 200 characters, with an entity, a space before a colon or line breaks is printed whole on one line and passes the check; a footer whose address runs over several lines, was wrapped, has a blank line added or lost its unsubscribe line is replaced whole; a footer edited beyond recognition, or own unsubscribe wording without the current address, is refused with the edit hint, counts as needing an edit and is not retried or sent; only the exact 1.2.0 notes count as waiting, in `CampaignFiller::needsEdit()` and in the Grow-now SQL count; a signature line with a "·" is not taken for the footer; the changelog states when the drafts are approved automatically).

## End-to-end run against a real WordPress

1. Create a throwaway WordPress install (MySQL or the SQLite Database Integration plugin), install the plugin (symlink `ppc-link-growth-engine/` into `wp-content/plugins/`).
2. Add a must-use plugin that routes `*.test` hosts to the fixture server (see `tests/integration/mu-plugin-example.php`).
3. Start the fixture server:
   ```bash
   PPCLG_FIXTURE_LOG=/tmp/ppclg-fixture-submissions.log php -S 127.0.0.1:8788 tests/fixtures/router.php
   ```
4. Run:
   ```bash
   PPCLG_WP_PATH=/path/to/wordpress PPCLG_FIXTURE_LOG=/tmp/ppclg-fixture-submissions.log php tests/integration/run.php
   ```

The run activates the plugin, discovers the fixture sites through an offline search provider, evaluates and scores them, packages and (after explicit authorisation) submits a listing to the fixture form, verifies the listing, monitors backlinks, drafts/approves/sends outreach (captured, not delivered), processes a reply through the inbound webhook and an opt-out, exercises the REST API as admin and anonymous, ticks the scheduler and creates a backup. It exits non-zero on any failed check.

The run is offline: requests to `*.test` hosts go to the fixture server, `api.indexnow.org` is answered by a recorder, and every other host is refused. Its last section (`tests/integration/growth.php`, helpers in `growth-fixtures.php`) covers the 1.1.0 features on the real WooCommerce install: it creates product categories, a tag and products that mirror the live store and checks that the storefront compliance check blocks, that `Policy` refuses automated submissions with `storefront_inconsistent`, and that a growth run driven through `POST /growth/start` and `POST /growth/step` completes with the submit step blocked, the verified opportunity database imported as owner tasks (595 minus skipped, no duplicates on re-import), IndexNow submitted with the expected JSON body, the key file served through `wp()`, the site audit finished, and an internal-link suggestion applied only through `POST /seo/links/apply` (a revision exists and only the anchor changed). It then renames the categories to research-only names, deletes the syringe product and the tag, and checks that the re-check passes and a second run's submit step is no longer blocked. Everything it creates is marked and removed at the end, and again at the start of the next run if a run was interrupted. The 1.2.0 section (`tests/integration/autopilot.php`) reproduces the live outreach settings (autosend on, individual approval on) and checks that a campaign created through `POST /outreach/campaigns` gets drafts for its matching prospects at once, that `POST /automation/autopilot` refuses without `confirm` (and `POST /settings` cannot switch it on), records the consent, approves waiting drafts and campaigns, that the send stage mails them, that a parked sender domain (DNS answered by the `ppclg_mail_domain_dns` filter) pauses sending and offers the site email, that a UTC WordPress uses Toronto time, and that switching Autopilot off returns unsent approvals to draft. The Build B section (`tests/integration/autopilot-links.php`) runs the internal_links job without a user (WP-Cron conditions, real kses): off it applies nothing; after `POST /automation/autopilot` it adds the link by itself with only the anchor changed (block comments, entities and UTF-8 identical), keeps a revision holding the previous content and audits it as `system:autopilot`; `POST /seo/links/undo-auto` refuses without `confirm` and then restores the post byte for byte, and the undone link is not added again. It then registers a stand-in competitor provider through `ppclg_backlink_sources` and checks that automatic detection keeps only real competitors, that Settings shows them apart from the owner list, that one removed there is not added back and that detection runs at most once every 30 days. The 1.2.1 section (`tests/integration/footer-refresh.php`) reproduces the live bug: drafts built while `outreach.postal_address` was "222 Jarvis st Toronto", the address corrected through `POST /settings` (nothing approved while Autopilot is off), the 1.2.0 note written on them; it checks that the campaign card counts them as waiting, that `POST /automation/autopilot` approves them with the new address once and the old line nowhere (only the footer changed, same token, one `outreach.footer_refreshed` audit entry each), that a draft built under the old address is approved at once when the address is saved in Settings under Autopilot, and that a brand change after approval is in the footer of the emails the send stage mails. Its second step saves a postal address over 200 characters with a line break through `POST /settings` and checks that the footer prints it whole on one line and the email goes out with it; then, for drafts built under the old address and edited through `POST /outreach/messages/{id}`, that a blank line added above the unsubscribe line still gets the whole footer replaced (the old address in no email), and that a footer with the "·" replaced is refused with the edit hint, counts as needing an edit on the card and is not mailed.
