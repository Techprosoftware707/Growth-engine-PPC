```bash
bash bin/lint.sh
bash bin/test.sh          # or: php bin/phpunit.phar
```

## End-to-end run against a real WordPress

1. Create a throwaway WordPress install (MySQL or the SQLite Database Integration plugin), install the plugin (symlink `ppc-link-growth-engine/` into `wp-content/plugins/`).
2. Add a must-use plugin that routes `*.test` hosts to the fixture server (see `tests/integration/mu-plugin-example.php`).
3. Start the fixture server:
   ```bash
   PPCLG_FIXTURE_LOG=/tmp/ppclg-fixture-submissions.log php -S 127.0.0.1:8788 tests/fixtures/router.php
   ```
4. Run:
   ```bash
   PPCLG_WP_PATH=/path/to/wordpress PPCLG_FIXTURE_LOG=/tmp/ppclg-fixture-submissions.log php tests/integration/run.php
   ```

The run activates the plugin, discovers the fixture sites through an offline search provider, evaluates and scores them, packages and (after explicit authorisation) submits a listing to the fixture form, verifies the listing, monitors backlinks, drafts/approves/sends outreach (captured, not delivered), processes a reply through the inbound webhook and an opt-out, exercises the REST API as admin and anonymous, ticks the scheduler and creates a backup. It exits non-zero on any failed check. `PPCLG_IT_ONLY=<part of a step title>` runs only the matching steps (plus activation and configuration), e.g. `PPCLG_IT_ONLY=1.2.4` for the server-pressure section. The activation starts the 10-minute quiet window after an update or activation (1.2.4); the activation step checks that and then moves the window into the past, so the rest of the run is not paused.

The run is offline: requests to `*.test` hosts go to the fixture server, `api.indexnow.org` is answered by a recorder, and every other host is refused. Its last section (`tests/integration/growth.php`, helpers in `growth-fixtures.php`) covers the 1.1.0 features on the real WooCommerce install: it creates product categories, a tag and products that mirror the live store and checks that the storefront compliance check blocks, that `Policy` refuses automated submissions with `storefront_inconsistent`, and that a growth run driven through `POST /growth/start` and `POST /growth/step` completes with the submit step blocked, the verified opportunity database imported as owner tasks (595 minus skipped, no duplicates on re-import), IndexNow submitted with the expected JSON body, the key file served through `wp()`, the site audit finished, and an internal-link suggestion applied only through `POST /seo/links/apply` (a revision exists and only the anchor changed). It then renames the categories to research-only names, deletes the syringe product and the tag, and checks that the re-check passes and a second run's submit step is no longer blocked. Everything it creates is marked and removed at the end, and again at the start of the next run if a run was interrupted. The 1.2.0 section (`tests/integration/autopilot.php`) reproduces the live outreach settings (autosend on, individual approval on) and checks that a campaign created through `POST /outreach/campaigns` gets drafts for its matching prospects at once, that `POST /automation/autopilot` refuses without `confirm` (and `POST /settings` cannot switch it on), records the consent, approves waiting drafts and campaigns, that the send stage mails them, that a parked sender domain (DNS answered by the `ppclg_mail_domain_dns` filter) pauses sending and offers the site email, that a UTC WordPress uses Toronto time, and that switching Autopilot off returns unsent approvals to draft. The Build B section (`tests/integration/autopilot-links.php`) runs the internal_links job without a user (WP-Cron conditions, real kses): off it applies nothing; after `POST /automation/autopilot` it adds the link by itself with only the anchor changed (block comments, entities and UTF-8 identical), keeps a revision holding the previous content and audits it as `system:autopilot`; `POST /seo/links/undo-auto` refuses without `confirm` and then restores the post byte for byte, and the undone link is not added again. It then registers a stand-in competitor provider through `ppclg_backlink_sources` and checks that automatic detection keeps only real competitors, that Settings shows them apart from the owner list, that one removed there is not added back and that detection runs at most once every 30 days. From 1.2.2 that section serves this WordPress over HTTP on its own address (`ppclg_it_self_server()` in `growth-fixtures.php` starts PHP's built-in server; the offline guard lets requests to that host through while it runs), because an automatic link now needs the item's public page to show the words. The 1.2.2 section (`tests/integration/render-check.php`) switches to a temporary classic theme whose `front-page.php` is hard-coded like the live one: a page gets its automatic link as an ordinary page; once it is the static front page the next run takes the link back out byte for byte (revision, `seo.internal_link_auto_removed` audit) and sets its suggestions aside as `not_shown` (listed by `GET /seo/links?status=not_shown&per_page=50` with the note); a post written by an administrator with an inline SVG and FAQPage JSON-LD stays refused while the consenting owner may not save unfiltered HTML (`map_meta_cap` filter) and is then linked as that owner with every other byte identical, the revision credited to the owner, the background user and the kses filters back. The theme, front-page settings and Autopilot are restored at the end. The 1.2.3 section (`tests/integration/link-rules.php`) reproduces the live Terms of Service case: an English Terms page with "belong to Pure Peptides Canada or its licensors", a French About page at `/fr/a-propos/` (a `page_link` filter stands in for the site's French plugin) with the focus keyword "pure peptides canada, fournisseur canadien de peptides, …" and `ppc_en_counterpart`, a home page with the focus keyword "peptides canada", and the two live suggestions stored as 1.2.2 made them next to a link a person applied earlier. After `run()` and `autoApply()` (automatic links on, no user) no link is added at the brand name, both suggestions are closed with their notes (also listed by `GET /seo/links?status=stale`), the person's link is untouched, the Terms page gets only its one valid automatic link with every other byte identical, a French page is offered the French About page by "fournisseur canadien de peptides", a French page at the site root (no `/fr/` address, no `ppc_en_counterpart`) is French by its text (offered the French About page, not the English product named in it), and the next runs add nothing. Against the 1.2.2 code it failed 9 of the 13 checks it had then (both live links are added). The 1.2.4 section (`tests/integration/server-pressure.php`) reproduces the live outage: it schedules a one-off `updraft_backup_resume` event (as a running UpdraftPlus backup does) and checks that a tick claims no job (a queued manual job stays queued with 0 attempts), enqueues no stage and completes nothing, that `Pipeline::status()`, `GET /automation/status` and `GET /overview` show "Paused: a backup is running (resumes automatically).", that the pause is logged once over two ticks, that `POST /automation/kick` queues no Action Scheduler action, that `POST /automation/run` still runs the stage with the warning, and that a Grow now run started through `POST /growth/start` waits at `POST /growth/step` (ok, waiting, `retry_after`, no step started or failed); after the event is removed the next tick runs the waiting job and logs the resume. It also checks that a leftover event of a backup whose `updraft_jobdata_<nonce>` says `finished` does not pause, that the same event pauses while that backup is still running, the `ppclg_backup_running` filter, the quiet window after a version change, and that `WP_Site_Health::get_tests()` lists the direct test "PHP's code cache (OPcache)" (good in the CLI, where OPcache is off). Against the 1.2.3 code 27 of its checks fail (the paused tick ran 19 jobs, the kick queued another tick and the Grow now step ran all 18 steps). The 1.2.1 section (`tests/integration/footer-refresh.php`) reproduces the live bug: drafts built while `outreach.postal_address` was "222 Jarvis st Toronto", the address corrected through `POST /settings` (nothing approved while Autopilot is off), the 1.2.0 note written on them; it checks that the campaign card counts them as waiting, that `POST /automation/autopilot` approves them with the new address once and the old line nowhere (only the footer changed, same token, one `outreach.footer_refreshed` audit entry each), that a draft built under the old address is approved at once when the address is saved in Settings under Autopilot, and that a brand change after approval is in the footer of the emails the send stage mails. Its second step saves a postal address over 200 characters with a line break through `POST /settings` and checks that the footer prints it whole on one line and the email goes out with it; then, for drafts built under the old address and edited through `POST /outreach/messages/{id}`, that a blank line added above the unsubscribe line still gets the whole footer replaced (the old address in no email), and that a footer with the "·" replaced is refused with the edit hint, counts as needing an edit on the card and is not mailed.
